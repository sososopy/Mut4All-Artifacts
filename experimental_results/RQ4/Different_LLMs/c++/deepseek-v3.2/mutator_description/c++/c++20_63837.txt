mutation operator: Convert a concept-constrained non-type template parameter pack to an unconstrained parameter pack with a trailing requires clause that replicates the concept constraint using decltype, targeting member templates of class templates (including static member templates) where the constraint is directly applied to the parameter pack.

This operator applies when the seed program contains a template (class or struct) with a member template (method or static member variable) that has a non-type template parameter pack constrained by a concept directly in its syntax, e.g., `template<Concept auto... xs>`. The mutation replaces the concept constraint in the parameter list with an unconstrained `auto... xs` and adds a `requires` clause after the parameter list that expresses the same constraint using `decltype(xs)` and fold expressions if the pack is used. The original concept name must be preserved as it exists in the program. The operator targets only member templates within class templates; if the enclosing class is not a template, it is not mutated.

Example: Original code: `template<class T> struct S { template<IsFoo auto... xs> void f() {} };`
Mutated code: `template<class T> struct S { template<auto... xs> requires (... && IsFoo<decltype(xs)>) void f() {} };`

If the parameter pack is not used in a fold in the original concept constraint (the concept is applied to each element individually), the requires clause should use a fold over the pack applying the concept to each `decltype(xs)`. The mutation does not introduce new variables, types, or functions; it only restructures the existing template syntax. This operator aims to expose bugs in the compiler's handling of concept constraints on non-type template parameter packs in nested template contexts, particularly during instantiation or explicit specialization.

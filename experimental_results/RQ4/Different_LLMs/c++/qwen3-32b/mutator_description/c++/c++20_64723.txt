Mutation Operator: ChangeConceptConstraintTargetType
Applies to requires clauses using a type conversion concept. Replace the target type in the concept constraint with a different type, triggering constraint evaluation path.
Example: In { __lhs == __rhs } -> convertible_to<T>, change T to another primitive type (e.g., int instead of bool). This forces the compiler to re-evaluate constraint satisfaction using a different conversion target.

Mutation Operator: InvertConceptConstraintNegation
Applies to requires clauses with negated concepts. Replace a negated concept constraint with a non-negated version, or vice versa. This alters constraint satisfaction evaluation logic.
Example: Change requires (not convertible_to<T>) to requires convertible_to<T> or vice versa. This must be applied to existing constraints that use negation operators in concept requirements.

Mutation Operator: ReplaceConceptWithAlternative
Applies to requires clauses using standard concepts. Replace a concept with another similarly named but differently implemented concept from the standard library.
Example: Replace convertible_to with same_as or derived_from when applicable. This forces the compiler to use a different constraint evaluation algorithm for the same code construct.

Mutation Operator: AddRedundantConceptConstraint
Applies to requires clauses without composite constraints. Add a redundant concept constraint using logical AND (&&) with a trivially true or false condition.
Example: Extend { __lhs == __rhs } -> convertible_to<bool> to { __lhs == __rhs } -> (convertible_to<bool> && is_same<bool>). This increases complexity in constraint evaluation paths.

Mutation Operator: SwapConceptConstraintOrder
Applies to requires clauses with multiple constraints. Swap the order of concept constraints in a composite requires expression.
Example: For requires (A() && B()), change to requires (B() && A()). This tests constraint evaluation order handling in composite requires clauses.

Mutation Operator: AddNestedRequiresClause
Applies to requires clauses without nested requires. Insert a nested requires clause within an existing requires expression.
Example: Transform requires (A()) into requires (A() && requires (B())). This adds additional constraint evaluation layers to test nested constraint handling.

Mutation Operator: ReplaceConceptWithUserDefined
Applies to requires clauses using standard concepts. Replace a standard concept with a user-defined concept with similar semantics.
Example: Replace convertible_to with a custom-defined concept that performs the same type check but with different implementation details. This tests concept implementation path handling.

Mutation Operator: AddConstraintToExistingRequires
Applies to requires clauses with minimal constraints. Add a new constraint to an existing requires clause using logical OR (||).
Example: Extend { __lhs == __rhs } -> convertible_to<bool> to { __lhs == __rhs } -> (convertible_to<bool> || is_void). This increases constraint evaluation possibilities.

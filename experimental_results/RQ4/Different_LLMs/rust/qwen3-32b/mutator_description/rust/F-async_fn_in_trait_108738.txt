Mutation Operator 1: Introduce async method in trait with await on another async method in the same trait, while using the 2018 edition and the `async_fn_in_trait` feature.

Target code construct: Trait definitions with async methods using `await` on other trait methods and using the `async_fn_in_trait` unstable feature.

Change to apply: 
In a trait definition that already contains at least one async method, introduce a new async method in the same trait. This new method must make an `await` call on another async method from the same trait. Ensure both methods are declared with the `async fn` keyword inside the trait and similarly implemented in the implementation block. Avoid using associated type parameters unless they already exist in the trait.

Example (Natural Language):
If the seed program contains a trait with a single `async fn` method, add a second `async fn` method inside the same trait. In the implementation block, write the second method to call the first method using `.await`, ensuring the name of the called method matches the trait method as in the example provided in the bug report. Keep the method signatures minimal and use types and variable names already present in the seed program.

Example (Pseudo-Code):
Original:
```
trait MyTrait {
    async fn foo(&self) -> i32;
}

impl MyTrait for i32 {
    async fn foo(&self) -> i32 {
        *self
    }
}
```

After Mutation:
```
trait MyTrait {
    async fn foo(&self) -> i32;
    async fn bar(&self) -> i32;
}

impl MyTrait for i32 {
    async fn foo(&self) -> i32 {
        *self
    }

    async fn bar(&self) -> i32 {
        self.foo().await
    }
}
```

This mutation operator targets a common structure in ICEs involving async methods in traits and is likely to expose bugs in the compiler's handling of type resolution and async method expansion.

mutation operator: Lifetime Elision Disruption in Trait Implementations
Target: This mutation operator applies to trait implementations where the trait definition includes explicit lifetime parameters. It specifically targets cases where the implementation attempts to elide lifetimes that are required by the trait, potentially across crate boundaries.

Application: For any impl block implementing a trait with one or more lifetime parameters (e.g., `trait Trait<'a, 'b>`), the mutation modifies the implementation header. It removes the explicit lifetime arguments from the trait path in the impl, forcing the compiler to attempt lifetime elision. If the impl is for a local type, it changes `impl Trait<'a, 'b> for Type` to `impl Trait for Type`. If the impl is for a remote type (a type defined in another crate), it performs the same removal. The mutation only applies if the trait definition itself is visible (i.e., in scope) and contains lifetime parameters. It does not apply if the impl already uses the `'_` placeholder or any explicit lifetime names; it only triggers when the lifetimes are explicitly bound to named parameters.

Example: Given a seed program where a trait `Reader<'a>` is defined and an implementation `impl Reader<'input> for MyParser` exists, the mutation would produce `impl Reader for MyParser`. This creates a mismatch: the trait requires a lifetime parameter, but the implementation omits it, prompting the compiler to attempt elision rules which may fail or trigger unexpected internal compiler paths, especially when associated async functions or types are involved.

Rationale: This directly models the bug scenario where a trait with lifetimes is implemented without providing the required lifetime arguments, leading to elision errors or internal compiler errors (ICE) during region checking or well-formedness checks, particularly with features like async functions in traits. The mutation stresses the compiler's logic for handling lifetime elision in complex trait matching scenarios.

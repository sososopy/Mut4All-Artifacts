mutation operator targeting transmutability checks with enum discriminants and variant layout. This operator applies to function calls where the function is a transmutability check (specifically using BikeshedIntrinsicFrom) and at least one of the type arguments is an enum type. The mutation alters the discriminant value assignment of an enum variant by replacing an explicitly assigned discriminant with a different explicit value, or by adding an explicit discriminant to a variant that does not have one, focusing on creating potential mismatches between the compiler's internal layout calculations and its discriminant handling during const-eval. The change is made to the enum definition within the seed program. If the seed program contains an enum with at least one variant, select one variant that either has no explicit discriminant or has an explicit integer discriminant. If the variant has no explicit discriminant, add an explicit discriminant equal to the value 1. If the variant already has an explicit integer discriminant, replace that integer with the value 1. This mutation should only be applied if the enum is used directly or indirectly in a transmutability check (i.e., as part of a type involved in a BikeshedIntrinsicFrom bound). The operator must ensure that any new integer literal introduced is of the default integer type (i.e., i32). For example, if the seed program contains an enum definition like 'enum Example { A, B = 5, C }', and this enum is used in a transmutability context, the operator could mutate variant 'A' to 'A = 1', or mutate variant 'B = 5' to 'B = 1', or mutate variant 'C' to 'C = 1'. The choice of variant should be deterministic, such as the first variant in the enum definition. This operator aims to trigger discriminant-handling bugs in const-eval during transmutability analysis by creating enum layouts where the computed discriminant index does not match the stored discriminant value.

Mutation operator: Invert the order of generic arguments and associated type bindings in method return types.

This mutation operator targets method signatures where the return type is a generic type with associated type bindings (e.g., Iterator::Item). It applies when a method's return type is explicitly specified as a path that includes both generic arguments and associated type bindings using the `=` syntax (e.g., `std::slice::Iter<Item = T>`). The operator swaps the positions of the generic argument and the associated type binding if both are present and separated by a comma. Specifically, if the return type is written as `Path<GenericArg, Item = Type>`, it mutates to `Path<Item = Type, GenericArg>`. If the return type is `Path<Item = Type>` with no additional generic arguments, this operator does not apply.

The change is made only to the method's return type annotation. The operator uses the existing path, generic arguments, and associated type binding from the seed program; no new elements are introduced.

Example: In a seed program with a method `fn iter(&self) -> std::slice::Iter<T, Item = U>`, the mutated version becomes `fn iter(&self) -> std::slice::Iter<Item = U, T>`. Another example: if the seed has `fn foo(&self) -> std::vec::IntoIter<Item = X, Y>`, it becomes `fn foo(&self) -> std::vec::IntoIter<Y, Item = X>`. This reordering is syntactically valid in Rust but may expose compiler bugs in metadata decoding or associated item resolution, as seen in the bug report where an invalid generic argument order triggered an ICE.

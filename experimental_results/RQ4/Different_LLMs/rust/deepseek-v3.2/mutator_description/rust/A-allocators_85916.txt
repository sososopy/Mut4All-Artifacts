Mutation operator: Change the order of type parameters in generic functions or structs that involve allocators or memory management, particularly those using MaybeUninit or raw pointers.

This mutation operator targets generic functions, structs, or trait implementations that use allocator-related types like MaybeUninit, raw pointers (*mut T, *const T), or allocator traits (Allocator). It applies when the seed program contains such generic definitions with multiple type parameters, especially where the order of parameters might affect compiler internal handling, such as during monomorphization or layout computation. The mutation swaps the positions of two type parameters in the definition. For example, if a struct is defined as Struct<A, B> where A is MaybeUninit<T> and B is an allocator type, change it to Struct<B, A>. Similarly, for a function fn f<X, Y>(...), swap X and Y in the signature. The changes must be consistent: all uses of the swapped parameters within the definition body must also be updated to reflect the new order. This mutation should not introduce new types or variables; it only reorders existing ones. For instance, given a seed snippet: struct Guard<T, A> where A: Allocator { ptr: *mut T, alloc: A }, mutate to struct Guard<A, T> where A: Allocator { ptr: *mut T, alloc: A }—note that the field types remain correct relative to the new parameter order. This can expose bugs in compiler assumptions about parameter ordering in contexts like trait resolution or type layout, which may trigger ICEs similar to the allocator API issue.

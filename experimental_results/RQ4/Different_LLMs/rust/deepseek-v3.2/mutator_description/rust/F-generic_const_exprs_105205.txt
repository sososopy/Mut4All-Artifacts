mutation operator: Replace a constant expression used as a const generic argument with a constant expression that references a const generic parameter from an outer scope, which is not in scope at the point of the constant expression, but syntactically similar to a valid parameter name.

This mutation operator targets const generic arguments in function calls, struct instantiations, or type annotations where the argument is a constant expression. It applies when the program uses the feature generic_const_exprs and contains at least one const generic parameter in an outer function or struct definition. The operator replaces the original constant expression (which could be a literal, a simple arithmetic expression, or a const parameter from the current scope) with a new constant expression that uses a const generic parameter name that is defined in an outer scope but is not accessible in the current context due to nesting or shadowing. For example, if there is an outer function with const parameter N, and an inner constant expression that does not have access to N (e.g., because it is in a nested generic context where N is not in scope), the operator replaces the inner constant expression with an expression containing N. The new expression should be syntactically valid but semantically incorrect due to the out-of-scope reference.

The change must use variable names, type names, or const parameter names that already exist in the seed program. If no suitable outer const parameter exists, the operator does not apply. The operator should avoid introducing new declarations; it only modifies existing constant expressions.

Example: In the seed program, function substs3 has const parameter L. Inside substs3, there is a call substs2::<{ Substs1([0; N + 1]) }>(). Here, N is not in scope (it belongs to zero_init). The mutation could change this call to substs2::<{ Substs1([0; L + 1]) }>(), but note that L is in scope. To trigger the bug, we need a scenario where the referenced parameter is from an outer scope but not directly accessible. Suppose we have an outer function with const parameter M, and inside substs3 we reference M. Since M is not in scope for substs3, this would be an error. However, to keep the mutation within the existing names, we can reference a const parameter from a different function that is not in scope. For instance, if the seed had another const parameter K in a parent context, we could use K. Since the seed does not have such a parameter, we must adapt: we can introduce a new const parameter in an outer scope if necessary, but per the rules, we prefer using existing names. If no outer name exists, the operator does not apply. In the given bug report, the error is due to using N which is not in scope. The mutation should replicate this pattern: take a constant expression that uses a const parameter correctly (e.g., using L) and replace it with an expression using a const parameter from a different, non-accessible scope (e.g., using N or M from an outer function). Specifically, locate a constant expression that is a const generic argument (like in a function call or struct type) and replace one of its identifiers with an identifier that names a const generic parameter from an outer function that is not in scope at that point.

To apply: Identify a const generic argument expression in the seed program. Check if there exists a const generic parameter defined in any outer scope (e.g., in an enclosing function or struct) that is not in scope at the location of the expression. Replace the entire constant expression with a new constant expression that references that outer parameter in a syntactically plausible way (e.g., use it in an arithmetic expression similar to the original). If multiple outer parameters exist, choose one that is not in scope. If none exist, skip mutation.

Illustration with pseudo-code: Suppose seed has: fn outer<const X: usize>() { fn inner<const Y: usize>() { let _: [u8; X]; } } Here, X is not in scope for inner. The mutation could change the type to [u8; X] (if it was originally [u8; Y]) to reference the outer X. This mimics the bug where a const expression uses an out-of-scope parameter, potentially triggering unsupported wfness checks.

In the bug report example, the error is due to using N in substs2::<{ Substs1([0; N + 1]) }>() where N is not in scope. The mutation operator would thus look for similar patterns: find a const generic argument that is a constant expression, and replace it with an expression that uses a const parameter name from an outer scope that is not available, aiming to cause an ICE during wfness checking.

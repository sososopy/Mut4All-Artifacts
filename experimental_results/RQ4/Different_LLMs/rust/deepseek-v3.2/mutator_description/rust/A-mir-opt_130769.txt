mutation operator: Change the pattern ordering in match expressions involving nested Result and Option types to expose edge case handling in MIR validation. This operator targets match statements where the matched expression is of a type like Poll<Result<Option<T>, E>> or similar nested enums (e.g., Result<Option<T>, E>, Option<Result<T, E>>). It applies when a match expression has multiple arms that destructure these nested enums. The mutation swaps the order of two match arms that handle different variants of the outermost enum but similar inner variants, particularly aiming to place an arm that handles an inner Err or None case before an arm that handles an inner Ok(Some(_)) case. Specifically, if the seed program has a match arm for Poll::Ready(Ok(Some(_))) and another for Poll::Ready(Err(_)), the mutation will swap these two arms. The goal is to create a different control flow graph that may trigger inconsistencies in MIR validation related to cleanup edges and unwind invariants. Only use variables, types, and patterns that already exist in the seed program. Do not introduce new names. For example, if the original code has: match val { Poll::Ready(Ok(Some(_trailers))) => {}, Poll::Ready(Err(_err)) => {}, Poll::Ready(Ok(None)) => {}, Poll::Pending => {} } then after mutation it becomes: match val { Poll::Ready(Err(_err)) => {}, Poll::Ready(Ok(Some(_trailers))) => {}, Poll::Ready(Ok(None)) => {}, Poll::Pending => {} } This reordering should be applied to the first two arms that differ in the inner Result (Ok vs Err) or inner Option (Some vs None) while keeping the outer variant (e.g., Poll::Ready) the same.

Based on the bug report, Rust compiler bugs labeled F-inline_const are more likely to be triggered by edge cases involving inline const blocks, especially when these blocks contain items that are not typically allowed or fully supported within const contexts, such as intrinsic functions or operations that require special handling by the compiler's MIR shim generation. The bug specifically occurs when the compiler attempts to create a shim for an intrinsic function (core::mem::transmute) placed directly inside an inline const block without proper surrounding expression context.

mutation operator: Replace inline const block expression with a standalone intrinsic call inside the const block. This operator targets inline const blocks that contain expressions. It replaces the entire content of an inline const block with a direct call to an intrinsic function, using types that are present in the seed program. The operator applies when the seed program contains at least one inline const block (identified by the const { ... } syntax) and at least one pair of types (which could be primitive types like i32, u8, or user-defined types) that are valid for the chosen intrinsic. First, identify all inline const blocks in the seed program. For each block, examine the surrounding context to find available types. If the seed program uses any intrinsic functions (like std::mem::transmute, std::intrinsics::rotate_left), use one of those intrinsics; otherwise, use std::mem::transmute as it is a common intrinsic. Select two types from the seed program that are of the same size (to avoid immediate compile errors unrelated to the bug) and for which transmute is potentially valid (e.g., both are integer types of the same size, or both are references). Replace the entire content of the inline const block with a call to the chosen intrinsic with these two types. If the original const block was used in an expression context (e.g., let x: u8 = const { ... };), ensure the mutated block remains syntactically valid by keeping the const {} wrapper, but with the new content. The mutation should not introduce new variables or types beyond those already present. Example transformation: Original code contains const { 5 + 3 }; and available types are u8 and i8. Mutated code becomes const { std::mem::transmute::<u8, i8>(0u8) };. Another example: Original code has const { some_function() }; and types u32 and f32 are present. Mutated code becomes const { std::mem::transmute::<u32, f32>(0u32) };. This mutation aims to trigger shim generation for intrinsics within inline const blocks, potentially exposing ICEs similar to the reported bug.

mutation operator

Target code construct: match expressions with constant patterns where the constant's type is an associated type from a trait implementation, and the constant's value is a literal integer that is not of the expected type of the associated type. Applies to match arms where the pattern is a constant path expression (like a const item) that resolves to an associated type projection, and the scrutinee expression is of a different integral type.

Change: Replace the constant pattern in the match arm with a different integer literal that is still within the same syntactic category (e.g., same base like decimal) but changes the numeric value. The new integer literal should be chosen such that it likely remains type-incompatible with the associated type's expected type if the original was incompatible, or may become incompatible if the original was compatible. Use an integer literal that exists elsewhere in the seed program as a literal of the same type as the scrutinee if possible; otherwise, use a small integer like 0 or 1. The constant definition itself is not changed; only the pattern in the match arm is mutated.

Example: If the seed contains `match x { CONST => 2, _ => 3 }` where CONST is a const of type `<SomeType as Trait<Param>>::Assoc` with value 3, and x is of type isize, mutate to `match x { 0 => 2, _ => 3 }` or `match x { 1 => 2, _ => 3 }`, where 0 or 1 is an integer literal of type isize (inferred from context). This changes the pattern from a constant of associated type to a literal of the scrutinee's type, potentially triggering type mismatches during const-eval or pattern checking.

Steps: Identify a match expression in the seed program. For each arm where the pattern is a single path expression that resolves to a const item, check if the const item's type is an associated type projection (like `<Type as Trait<T>>::Assoc`). If so, replace that pattern with an integer literal. Choose the integer literal value as follows: if the scrutinee expression has a numeric type (like isize, i32, u8, etc.), use a literal of that type (e.g., 0isize or just 0 if inferred). Prefer to reuse an integer literal that appears elsewhere in the same function or module for the same type; if none exists, use 0. Ensure the literal is syntactically valid (e.g., no suffix if the type is inferred). This mutation may cause a type error if the associated type is not compatible with the scrutinee's type, potentially exposing ICEs in const-eval or pattern matching.
